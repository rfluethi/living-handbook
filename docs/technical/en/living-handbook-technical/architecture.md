# Architecture

A concise, developer-facing summary of the shipped design. For a gentler, plain-language tour aimed at anyone who does not know the code yet, see [code-overview.md](code-overview.md).

## Building blocks

- **Content type `handbook`**: the handbook pages. Hierarchical, so parent and order drive the navigation. Registered non-public (`public => false`, `publicly_queryable => true`) and kept out of the sitemap, feeds and oEmbed, so an internal handbook does not leak to logged-out visitors. Single pages stay reachable and access-guarded at `/handbook/<slug>/`. The post type archive is switched off (`has_archive => false`): the overview is a normal page holding the overview block, so there is no second, competing overview you cannot style.
- **Taxonomies**: page type (Diataxis plus FAQ), topic, responsible role, audience. All four are plain classifying taxonomies for filtering and search; they have nothing to do with the navigation.
- **Handbook grouping (`handbook_set`)**: each page belongs to exactly one handbook, enforced when the terms are written (`Handbooks::enforce_single()`), because the block editor renders a hierarchical taxonomy as checkboxes and would otherwise let a page land in two: choosing a second handbook moves the page rather than adding to it. Which handbook a page belongs to is answered in one place, `Handbooks::for_post()`, by the lowest term id, so renaming a handbook cannot move pages between navigation trees. A handbook carries an access configuration and gets its own entry page at the term archive, `/handbook-set/<slug>/`.
- **Access**: three levels per handbook: public, all members, or restricted to roles and/or people. Enforced through a single central check, `AccessController::can_view_post()`, used by every read path (single view, entry page, search, result sets, REST, the facet endpoint, the feedback endpoint, the comment channels, the menu and the overview), and filterable via `living_handbook_can_view_post`. This check is the one mandatory gate: any programmatic or AI reader added later must route through it rather than query the database directly. It is deliberately fail-closed, so a page without a handbook is readable only for accounts with `edit_others_posts` (Editor) and for administrators, and a page that from older days still sits in two handbooks must be allowed by both. Two exceptions come first. Whoever reads every handbook, `AccessController::reads_everything()`, by default an account with `manage_options` (Administrator, changeable through `living_handbook_read_all_capability`), reads every handbook in full, whatever the handbook says: every page, one without a handbook too, and on the handbook level (`can_view_term()`) the entry page, the entry in the overview and the learning paths. Everyone else, editors included, reads what a handbook grants them; a restricted handbook without the Editor role ticked is therefore kept to administrators. Grants exist per handbook, not per page. And whoever may edit a page under the WordPress rules (`edit_post`) may also read it, even when the handbook otherwise excludes them and even when the page belongs to no handbook yet. Editing in wp-admin needs this: the block editor loads a page through the REST API with `context=edit`, and the preview is a single view. Both guards therefore check `edit_post` beside `can_view_post()`, not inside it, so the filter cannot take this exception away. For Authors this covers only their own pages, for Contributors only their own drafts, and for other people's pages in a handbook the person may not read the plugin itself denies `edit_post` (see below). This second exception is per page: other people's pages, lists, search and navigation still follow the handbook's rules. A denied front-end request answers a guest with the login, and a signed-in user with a 403 and an explanation, or a redirect to the page chosen under Settings, Access. Media inherits the visibility of the page it is attached to, so an image of an internal handbook is not listed or readable through the media endpoint; whoever may edit the page gets its files too, through the media endpoint and on the attachment page; the file itself lies, for a handbook that is not public, in a protected folder that a server rule sends to WordPress, and the plugin hands it out after `can_view_post()` of the parent page (see [protected-files.md](protected-files.md)).
- **Access in the back end**: the same rule holds in wp-admin for other people's pages. Pages by other people in a handbook the person may not read are left out of the page list, for `get_posts()` too (`restrict_query()` sets `post__not_in` on back-end queries for this, because `get_posts()` suppresses filters), their files are left out of the media library (`filter_posts()`), and `guard_meta_caps()` on the `map_meta_cap` filter denies `edit_post`, `delete_post` and `read_post` for them: no editor, no deleting, no reading. One's own pages always stay visible and editable; pages without a handbook and pages in readable handbooks appear as usual. For such a handbook itself `guard_meta_caps()` denies `edit_term`, `delete_term` and `assign_term`: nobody changes its visibility, roles, people or name, deletes it or assigns pages to it without being allowed to read it, `manage_categories` or not. It is left out of the handbook list (`hide_handbooks_on_term_screen()`), out of the taxonomy's REST list the block editor builds its picker from (the single read answers 403), and out of the plugin's own pickers (import target, export, "Move into a handbook…", list filter). Import, export and the move check the chosen handbook once more on submit with `AccessController::may_use_handbook()`. Comments follow their page: in wp-admin, the comment screen included, a comment shows when its page would show in the page list (one's own pages always, other people's unless they sit in a handbook the person may not read); on the site, in the comment feeds and over REST it follows `can_view_post()`, without the `edit_post` exception; whoever reads every handbook sees all of them. The cache key of a comment query carries a fingerprint of that rule (`cache_domain`), so a persistent object cache does not hand one reader's comments to another. One limit: the counts above the page list ("All (12)") still count every page, the hidden ones included. The file itself does not reach the person under its address either; since 0.79.0 it lies in the protected folder.
- **Privacy tools**: `Privacy/Privacy.php` connects the plugin's personal data to Tools → Export Personal Data and Erase Personal Data, to the privacy policy guide and to account deletion. Three places hold user ids: the voter list of a page, its reviewer, and the access list of a handbook (`living_handbook_users`). The exporters name all three; the access exporter lists the handbooks whose list holds the person. The eraser takes the person out of the voter lists and keeps the reviewer and the access list, reporting both: the reviewer is the page's editorial record, and emptying an access list would silently end an active account's access. A deleted account leaves every voter list and every access list.
- **Custom fields**: two kinds, told apart by their name. The editorial fields a person fills in are public and carry the `living_handbook_` prefix; everything the plugin keeps about a page rather than for it (where it came from, how it syncs, import bookkeeping, feedback counters) is protected and carries `_lh_`, so it stays out of the Custom Fields box where a wrong edit would break the sync without a word. Older installations are renamed to those names by `Plugin::maybe_upgrade()`. Every key, with its type, its writer and whether it is exposed, is listed in [meta-fields.md](meta-fields.md).
- **Metadata**: native custom fields for last update, last review, review interval and reviewer, plus an AI-exclusion flag (`living_handbook_ai_exclude`). An aggregated read-only REST field, `living_handbook_status`, exposes the derived freshness (due/overdue), the review data, the permalink and the exclusion flag in one place.
- **Maintenance**: an overdue dashboard with a percentage and escalation, plus a per-page feedback counter. The feedback endpoint requires a user who is allowed to read that page and counts one vote per signed-in user and page; with the **Public feedback** setting on, guests vote on public pages too, without deduplication and under an hourly ceiling per page. See [rest-routes.md](rest-routes.md).
- **Navigation**: a self-contained, collapsible page tree per handbook, built from the page hierarchy and styled by the plugin (no other plugin required). The title row has the same form as every row with subpages: a toggle button on the left, the handbook title beside it as an ordinary link to the entry page. No native `<details>` and no arrow; the closed state is the class `.living-handbook-nav.is-collapsed`. A Menu display shows the whole tree, an Accordion display collapses branches. The tree is built fresh on every request and deliberately not cached: its markup carries the current page and its open branches, so a cache would need an entry per page and per viewer. What it costs is reading the pages behind it, not the markup. The tree therefore reads only the columns it needs (title, slug, parent, order, status, password, type, date), not the content, and never puts these partial posts into the post cache; it loads the parent pages whole, in one query, because `get_permalink()` builds the hierarchical address from them. The area cards of the entry page and the page preview on the handbook cards of the overview *are* cached, per handbook and per viewer, keyed on a shared version counter that is bumped whenever a page or a handbook term changes. Optionally the accessible handbooks are injected into the theme's own Navigation block via the `has-handbook-menu` class.
- **Import**: an import screen turns Markdown into handbook pages. A Markdown library (league/commonmark) produces HTML, and WordPress's own paste conversion turns that into editable blocks. Sources: a pasted draft, a ZIP of `.md` files (flat, or structured along a `mkdocs.yml` nav), and GitHub file or folder URLs. A ```` ```mermaid ```` fence becomes a dedicated live-rendered block, collapsible sections become details blocks, and images from `assets` are sideloaded into the media library. A shared post-processor applies the transport metadata and resolves parents and internal `.md` links. Re-importing the same source updates the existing pages instead of duplicating them, matched by source path, slug within the handbook, or source URL. See [import-and-sync.md](import-and-sync.md).
- **Transfer between sites**: a handbook, or one area of it (a top-level page and its descendants), can be exported as a self-contained bundle: a ZIP holding a `manifest.json` and the referenced media. The manifest carries the handbook configuration, every page as a block-markup snapshot with a stable hierarchy key and an origin id, the four classifying taxonomies, the freshness data and the per-page source, so a GitHub-backed page resumes syncing on the target, and the handbook's learning paths (`paths`), their lessons as bundle keys. Import matches a page by origin id, then bundle key, then slug within the target handbook (an import as ordinary pages by origin id and bundle key only), changes a match only when the importing person may edit it, and what happens on a match is a run rule the importer chooses: skip (the default, never overwrite), update, or always create. A page flagged `_lh_import_protected` is never overwritten, nothing is ever deleted, local operational data (feedback counts, review data) survives an update, and a handbook created by the import starts at "members" visibility whatever the bundle says. Both screens require `edit_others_posts` and work only with handbooks the person may read; a bundle whose handbook already exists and is not readable for the person is refused. See [import-and-sync.md](import-and-sync.md).
- **Handing a handbook out**: a handbook, or one area of it, also exports as a static website: a ZIP of plain HTML files that opens from the file system, with one file per page, the uploads it references, a page tree, a table of contents built on the server and a search index as a script rather than a fetch, because a `file://` document may not fetch its neighbours. Pages are rendered in process rather than fetched over HTTP, so the access check runs against the exporting user instead of a logged-out visitor, and the render runs in passes with a time budget, resumed from a transient keyed by a job id. The result carries no access rules of its own, which the screen says plainly. `edit_others_posts` and a readable handbook, like the bundle. See `Export/StaticSite.php`.
- **GitHub sync**: the source of a page is selectable per page (`_lh_source`, values `wordpress` or `github`). GitHub pages carry a Markdown source URL (`_lh_source_url`), are pulled from the repository (on save, via "Sync now", and via WP-Cron on a configurable schedule, in bounded batches), stored as rendered HTML filtered through `wp_kses`, and locked in the editor. Neither key is in the REST API, and writing them takes `edit_post` and `upload_files`, like the Source box. The source URL is restricted to an allowlist of hosts to prevent server-side request forgery. A block marks the public page, a column in the list table shows the source, and failed syncs are flagged and surfaced as an admin notice. Live sync covers public repositories; private repositories are imported from a ZIP instead.

## Principles

- No external WordPress plugin dependencies. A block theme is expected; no other plugin is required.
- Composer runtime dependencies only as a deliberate exception for the import and sync module: league/commonmark (Markdown, BSD-3-Clause), symfony/yaml (reading `mkdocs.yml`, MIT), and enshrined/svg-sanitize (sanitising imported SVG images, GPL-2.0-or-later), all open source and free. The build ships them in `vendor/`, moved into `LivingHandbook\Vendor\` by PHP-Scoper so they cannot collide with a copy another plugin loads; `Support\Vendored` resolves the names, because a development checkout has them unprefixed. mermaid.js is bundled in `assets/js/` for the diagram block (MIT).
- Standard WordPress interfaces (REST, hooks) behind the access check. The plugin's own REST routes are listed in [rest-routes.md](rest-routes.md).
- Cost is measured, not guessed. `bin/seed-performance.php` builds a handbook of 2000 pages and `bin/measure-performance.php` renders the entry page, a single page and the navigation tree, cold and warm, reporting queries, time and every query that repeats; see [CONTRIBUTING](https://github.com/rfluethi/living-handbook/blob/main/CONTRIBUTING.md). The rule that comes out of it: nothing may cost a query per page. Where a code path reads posts or terms one row at a time, it goes through the WordPress caches (`get_the_terms`, `_prime_post_caches`) instead of around them, and where a maintenance pass needs the whole handbook it reads it once into a lookup table. Integration tests hold that line, each counter-checked to fail without the fix: `AccessQueryCostTest`, `ImportLinkCostTest`, `ExportQueryCostTest`, `PageTreeCostTest` (the tree loads no page content), `ParentPrimingCostTest` (lessons, search and filter results read the parent pages at once), `LearningPathCostTest` and `OverviewCostTest`.
- Configuration follows "decisions, not options": visual choices belong in the Site Editor, behaviour options are few and justified, everything else is a hook.
- English is the language of the repository. The German translation lives in `languages/`; the German user handbook (`docs/user/de/`) and the German technical documentation (`docs/technical/de/`) ship in the repository next to their English counterparts. Neither language is the source of the other: they are separate texts, and a change to one is a change to both (see [`docs/README.md`](https://github.com/rfluethi/living-handbook/blob/main/docs/README.md)).
